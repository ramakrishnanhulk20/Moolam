Repeated review passes, 2026-09-25 to 2026-09-27
The same AI code review prompt was run again and again over each part of Moolam until a pass found
nothing new at medium or high. Monad's advice for builders was that one review pass is not enough,
because the same reviewer finds different bugs on different runs. This file is the record of that
loop: how many passes each part took, what they found, and the commit that fixed each finding.

The rule
1. One prompt, word for word the same on every pass. Only the area and the output file change.
2. Each reviewer reads the threat model first (docs/security/threat-model.md), then every file in
   its area, and reports real bugs only: wrong results, security holes, broken failure handling, loss
   of money or data, a wrong on-chain state, a screen that could say something untrue, a limit that
   does not hold. No style notes. Each finding carries a severity, a confidence, a file and line, a
   concrete input that shows it, and a one-line fix.
3. Reviewers cannot see earlier passes, and they never edit code, send a transaction or start a
   server. Many ran the code they were reading, in memory, to prove a finding.
4. From pass 4 on, every finding was first shown with a test that failed on the old code, then
   fixed, and the whole suite had to pass before the commit. A finding that did not reproduce
   was marked rejected.
5. An area stops when a pass adds no new finding at medium or high. Lows found on the last pass are
   fixed anyway.

The prompt, in short
Review AREA of the Moolam repository for real bugs. Read docs/security/threat-model.md first for
the intended invariants, then read every file in AREA. Report only real bugs: wrong results,
security holes, broken failure handling, loss of money or data, wrong on-chain state, a screen or
record that could state something untrue, a limit that does not hold. No style, no naming, no "add
more tests", no hypothetical hardening without a concrete path. When unsure, say so in the
confidence field; never inflate. At most 25 findings, most severe first, each with severity,
confidence, file:line, title, what goes wrong, a concrete input or sequence, and the fix in one line.

What the verify service passes found, in short
- Highs: an unbounded metadata read, a route that refused every real caller, a copied fingerprint
  outranking the original, and a decoder that leaked memory on crafted CMYK files. All fixed.
- Privacy: camera GPS surviving in segments other than EXIF, and a camera's own C2PA record carrying
  location and serial. The pinned file now keeps only what decodes the pixels, and a camera's record
  is kept with those assertions redacted, or dropped when redaction is not clean.
- Money: a paid answer lost when the facilitator timed out, one transfer proving several payments, a
  payer asked to pay twice. Each paid answer is now proven from the asset's own AuthorizationUsed log
  and the Transfer right after it, for the exact signed value.
- Honesty: an expired signing certificate reading as a tampered file, a stale index answering "no
  match" as if current, facts shown as current when a minute old. Answers now carry when each fact
  and the index copy were read, and say so when the register copy is behind.
- Availability: uploads held open to lock others out, one caller holding every decode turn, a memory
  leak in the fingerprint worker. Uploads are now counted byte by byte against a ceiling per caller,
  turns are shared in rotation, and the worker is replaced before it can grow.
